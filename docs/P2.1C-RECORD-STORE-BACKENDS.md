## The question this document answers

P2.1a gave the fleet view a durable `RecordStore` with two implementations:
`MemoryRecordStore` (reference/tests) and `FileRecordStore` (atomic JSON file —
no CGO, no external service, one small file). The interface exists precisely so
the backend can change without the service learning about it.

The plan's acceptance criterion names "SQLite (dev) and Postgres (prod)" behind
that interface. Before writing either, this document settles *whether we should*
— because every backend is a dependency, and this is a public repo whose whole
footprint today is **one** dependency (`gopkg.in/yaml.v3`). Adding a database
driver, or a CGO flag, is a decision that belongs in writing, not in a diff.

## What actually breaks with the JSON file

Be honest about the ceiling rather than discovering it in production:

1. **Whole-file rewrite per append.** `FileRecordStore.Append` marshals *every*
   retained record and rewrites the file. At the default cap of 10k records that
   is ~10k small objects rewritten on every single detected event. Fine for a
   quiet fleet; ugly during the exact moment this tool exists for — an incident,
   when events are *not* quiet and the file is being rewritten many times a
   second. The retention cap bounds the cost, but the cap is a band-aid over an
   O(n)-per-write design.
2. **Single writer, single process.** The file has no locking that is safe
   across processes (only an in-process mutex). A second central instance
   pointed at the same file corrupts it. Today central is single-instance, so
   this is latent, not live — but "the fleet view" implies more hosts, not more
   centrals, and an operator will eventually run two.
3. **No index.** `Recent(hostID, limit)` scans. At 10k records that is
   microseconds; the reason to reach for SQL is not today's scan, it is the
   *query that doesn't exist yet* — see the interface gap below.

## The interface gap (fix this before any backend)

`RecordStore` today has exactly two methods: `Append` and
`Recent(hostID, limit)`. That is enough for the fleet view as built, and no more.
A SQL backend would want, and an operator will ask for:

- **Time range** ("what fired between 02:00 and 03:00"). Without it, the only
  way to ask is to pull `limit` records and filter in the caller — which pushes
  the scan out of the store and defeats the point of having one.
- **Minimum severity** ("only high and critical"). Same argument.
- **Count/rollup** ("how many critical per host this week") — currently computed
  in `buildFleetView` from a full fetch.

**Decision:** widen the interface to a single `Query(ctx, RecordQuery) ([]Record,
error)` with optional fields (`HostID`, `Since`, `Until`, `MinSeverity`,
`Limit`), and keep `Recent` as a thin wrapper for the common "latest N" case.
This is deliberately **not** done in the same change as a new backend — the
interface change ships first, against the existing two implementations (whose
tests then pin the new behavior), so the backend lands against a settled
contract instead of moving one.

## Backend decision

### Not now: a database driver *by default*

The zero-dependency JSON file stays the **default**. A user who clones the repo
and runs the demo must not need a database, a CGO toolchain, or a network fetch
to see a detection. That is the same instinct as choosing a JSON file over
SQLite in P2.1a, and it holds.

### SQLite (dev / single-node) — **the next backend, behind a build tag**

- Driver choice matters more than the database here:
  - `mattn/go-sqlite3` — fastest, but **CGO**. Breaks the "clone and build"
    promise on a machine without a C toolchain, and complicates static builds
    for the collector. Rejected as the default.
  - `modernc.org/sqlite` — pure Go, no CGO. Larger dependency tree, but it
    builds anywhere `go build` does. **This is the choice** *if* SQLite is
    adopted.
- Still gated behind a **build tag** (`-tags sqlite`) so the default binary
  keeps a one-dependency footprint and the driver is opt-in, exactly as the
  eBPF adapter is gated behind `-tags ebpf`. A backend that is compiled in
  unconditionally is a backend you cannot choose to not ship.
- Satisfies: O(1)-ish append (WAL), cross-process locking, indexes on
  `(host_id, when)` and `(severity)`, real time-range queries.

### Postgres (prod fleet) — **scoped, not scheduled**

- Pure-Go driver (`jackc/pgx`) — no CGO.
- Needed when the record volume or the number of concurrent readers outgrows a
  single node, or when the fleet view must be served by more than one central.
- Higher operational cost (a service to run, credentials, migrations). It earns
  its place when a real fleet needs it, not before. This document scopes it; it
  does not build it.

## The migration question (why the doc exists at all)

Records are append-only and time-bounded (default 7 days / 10k). That means
**there is no migration**: point central at a new backend and it starts filling;
old JSON-file records age out. `fileStoreDoc`/`recordStoreDoc` already carry a
`Version` field for a future on-disk format change, but switching backends is a
config change, not a data migration. This is the payoff of the `RecordStore`
interface and the reason a database is a *backend*, not a *rewrite*.

## Acceptance (when a backend step is done)

- `-tags sqlite` build compiles and passes the **same behavioral test suite**
  the JSON file passes — the contract tests are backend-agnostic, parameterised
  over `RecordStore` implementations, and a new backend is "done" when it runs
  green against them unchanged.
- Default build (`go build ./...`, no tags) is unchanged: no new dependency, no
  CGO, JSON file default.
- `Query` honors `Since`/`Until`/`MinSeverity`/`HostID`/`Limit`; `Recent` is
  defined in terms of it.
- README documents the three backends and how to select each.

## Order of work

```
P2.1c-1  widen RecordStore to Query(...); Recent as wrapper      ▶ next
P2.1c-2  make the backend contract tests parameterised over impls
P2.1c-3  SQLite backend (modernc.org/sqlite) behind -tags sqlite
P2.1c-4  Postgres backend (pgx) — scoped, when a fleet needs it
```

Work stops after whichever step a real fleet actually requires. Steps 3–4 are
deliberately optional and gated, not a march toward a database the repo may
never need.
